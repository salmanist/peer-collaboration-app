2026-08-07 (later) — Added an official-student roster gate to registration.

Registering with an @lgu.edu.pk address is no longer sufficient on its own —
the email must also appear in a new accounts.StudentRoster whitelist table
(email only, unique). Loaded via a management command:
  manage.py import_roster <path-to-csv> [--dry-run]
The command looks for a column named "email" (case-insensitive) in the CSV
and ignores every other column, so the university's export can carry
whatever extra fields (student ID, name, etc.) it already has without a
custom importer. Re-running against an updated CSV is safe — existing
entries are left alone (get_or_create), only new emails are added.

suffix check and before the "already registered" check, with its own error
message ("This email isn't on the official LGU student roster..."). Nothing
else in the registration/verification/login flow changed — a roster hit
still requires setting a password and completing OTP verification, same as
before. StudentRoster is also registered in Django admin for manual
spot-checks, even though CSV import is the primary way it gets populated.

Verified: imported a 2-row test CSV (with extra ignored columns), confirmed
a roster email can register (201) and a same-domain but non-roster email is
rejected (400) with the new message. Test data cleaned from fyp_dev after.

2026-08-12 — StudentRoster became the full simulated university-API
record (prep work ahead of the Ride Sharing module).

Rationale: the roster CSV already stands in for a real university student
records API in this project (system_design.md's deferred-infra pattern —
same idea as the console email backend). Until now it only proved an email
was a valid student; everything else (name, department, enrollment year)
was typed by the registrant themselves, which meant nothing stopped someone
registering with a fake name. Since Ride Sharing needs a trustworthy gender
field to support a "same gender only" ride preference (raised mid-planning:
some riders, particularly female students, may not be comfortable sharing a
ride with the opposite gender), and self-reported gender at signup would be
just as spoofable as a self-reported name, the fix was to make the roster
the single source of truth for all of it.

What changed (backend/accounts/):
- StudentRoster gained full_name, department, enrollment_year (blank/null
  tolerated per-field) and gender (CharField, choices male/female, blank
  tolerated) alongside the existing unique email.
- User gained the same gender field, populated only at registration from
  the matched roster row — never accepted from the client, not in
  RegisterSerializer's fields, and marked read_only in UserSerializer so
  PATCH /auth/me/ can't change it either.
- RegisterSerializer.Meta.fields shrank to just ["email", "password"].
  validate_email() now fetches the matching StudentRoster row (not just an
  .exists() check) and stashes it on the serializer instance; create()
  pulls full_name/department/enrollment_year/gender off that row when
  building the User. Net effect: you can't register with a name that isn't
  on record.
- import_roster (manage.py import_roster <csv>) now optionally reads
  full_name/department/enrollment_year/gender columns (case-insensitive
  header match, same pattern as the existing email column), each
  independently optional so old email-only CSVs still import unchanged.
  Gender values are normalized (M/Male/male → male, same for female).
  Switched from get_or_create to update_or_create so re-running the import
  against a corrected/updated CSV actually refreshes existing rows instead
  of silently leaving stale data — matches "this is a live feed" semantics
  better than the old whitelist-only behavior.
- The /test/ dev console, DebugAddRosterView, and Django admin list/filter
  views were all updated to match (roster entries can now carry a name and
  gender when added ad hoc for testing).
- docs/api-contracts/auth.md updated: register request example is now
  email+password only, with a note that the rest comes from the roster;
  gender added to the documented User fields and to the read-only list on
  PATCH /me/.

Dummy dataset: backend/accounts/fixtures/dummy_students.csv, 30 rows
(email, full_name, department, enrollment_year, gender), @lgu.edu.pk
addresses, mixed CS/SE/EE/BBA departments, 2021–2024 enrollment years, an
exact 15/15 male/female split so both directions of the upcoming
same-gender-only ride filter have real data to exercise. Loaded with
`python manage.py import_roster backend/accounts/fixtures/dummy_students.csv`
— imported clean, 30 added, 0 invalid.

Verified via Django shell (RegisterSerializer exercised directly, not just
inspected): registering with only email+password against a roster row
(ali.raza@lgu.edu.pk) correctly produced a User with full_name="Ali Raza",
department="CS", enrollment_year=2022, gender="male" — none of which were
in the request payload. Migration (accounts.0003) applied cleanly against
the live Postgres db; existing/legacy roster rows without the new columns
remain valid (blank fields), confirmed by inspecting one such row after
running the import.

Known limitation carried forward: gender is binary (male/female) only, a
deliberate scope cut confirmed with the project owner rather than an
oversight — no third case exists to define same-gender-matching rules for.

2026-08-12 — Built the Ride Sharing module (backend + mobile), covering
SRS §4.1 REQ RS 01–05.

Backend (backend/apps/rides/, the first app under the new apps/ nested
package layout — accounts/common stay flat, everything from here on lives
under apps/):

- Ride: offerer FK, departure/destination text, departure_date/time,
  seats_total (1–8, validated) / seats_available, same_gender_only bool,
  is_cancelled bool, created_at.
- RideJoinRequest: ride + requester FK pair (DB-unique — one request per
  person per ride), status (pending/accepted/declined), created_at.
- Endpoints under /api/rides/: list+create (GET/POST), retrieve, join,
  cancel, list-requests (offerer-only), accept, decline. Full shapes in
  docs/api-contracts/rides.md.
- Search (REQ RS 02) is deliberately simple: departure/destination
  substring match + exact date, ordered chronologically — a named scope
  cut (no GPS/polyline), flagged in plans/ridesharing_plan.md as a gap to
  revisit with something smarter before final submission if time allows.
- Notifications (REQ RS 03) run through a new shared common.Notification
  model + notify(recipient, verb, target) helper — GenericForeignKey-based
  so it isn't tied to rides specifically; Zahra's Resource Sharing module
  can reuse it instead of building its own. Endpoints: GET
  /api/notifications/ (own feed), POST /api/notifications/<id>/read/.
- Accept (REQ RS 05) is race-safe: wraps the ride + join-request rows in
  select_for_update() inside a transaction, re-checks pending status and
  seat availability under the lock before decrementing — two offerers
  can't double-accept the last seat. Accept response nests both the full
  ride and the join request (with requester contact fields), and the
  requester's own GET on the ride shows my_request_status + the offerer's
  contact — both parties get each other's info once confirmed, per REQ
  RS 05.
- Cancel (addition beyond the original scope cut, confirmed with the
  project owner): offerer-only, blocked once any request on the ride has
  already been accepted (protects the REQ RS 05 confirmed-contact
  guarantee), notifies any still-pending requesters.
- Gender preference (addition raised mid-build — some riders, especially
  female students, may not want to share a ride with the opposite gender):
  same_gender_only is an offerer-side toggle. It's enforced twice — search
  results simply exclude a restricted ride for a mismatched or
  blank-gender caller (Q(same_gender_only=False) | Q(offerer__gender=...)
  in the queryset), and RideJoinView independently rejects a mismatched
  join attempt even via direct ID. An offerer with no gender on record
  can't turn the toggle on in the first place. This is the reason the
  accounts roster-record work (same day, earlier entry) exists — gender
  had to come from a trustworthy source, not a text field.

2026-08-17 — Moved the backend database off local Postgres onto a shared
Neon (serverless Postgres) project.

Rationale: salman and zahra were each running their own local Postgres
instance, which meant no shared data and a growing risk of schema drift
between machines as more modules land. Neon's free tier (100 compute-hours/
month, 0.5GB storage, auto-suspend on idle) is a drop-in Postgres swap with
no code rewrite needed, so both developers now point at one centralized
database instead of syncing dumps by hand.

What changed:
- config/settings/base.py: DATABASES.OPTIONS now sets sslmode from a new
  DB_SSLMODE env var (default "prefer", so local Postgres keeps working
  unconfigured for anyone still on it). Neon requires TLS, hence the
  explicit "require" value used against it.
- backend/.env (gitignored, never committed): DB_HOST/DB_USER/DB_PASSWORD/
  DB_NAME swapped from local fyp_dev/fyp_dev_user to the Neon project's
  pooled connection (the "-pooler" host, not the direct one — the pooled
  endpoint has a much higher concurrent-connection ceiling, needed since
  two developers plus Django's autoreload can open several connections at
  once against the free tier's low direct-connection cap).
- All existing migrations re-applied cleanly against the new Neon database
  (accounts, admin, auth, common, contenttypes, rides, sessions) — same
  schema, empty data (Neon started blank; nothing carried over from either
  developer's local fyp_dev, which stays as an untouched local fallback).

Free-tier discipline agreed for both developers: don't leave anything
polling the DB (health checks, open shells) since active connections block
auto-suspend and burn compute-hours; use the pooled connection string only;
don't create extra Neon branches (each one gets its own compute
allocation); keep seed/dummy data modest; coordinate migrations by pulling
before running `manage.py migrate` so schema state doesn't diverge, same as
before — Neon doesn't add or remove any of that coordination.

Verified: `manage.py migrate` ran clean against Neon end to end, and a
direct query (`SELECT current_database(), version()`) through Django's
connection confirmed the running server is actually answering from Neon's
`neondb` (Postgres 18.4), not a leftover local connection.

Known limitation: the Neon free tier auto-suspends the database after a
few minutes idle, so the first request after a gap pays a ~1s cold-start
cost — acceptable for dev/demo use, not something to design around.

2026-08-21 — Added free geocoding for ride locations, resolving the
text-substring-matching limitation flagged in the 2026-08-12 Ride Sharing
entry.

Context: asked whether Google Maps should be integrated for ride
pickup/destination. Full Google Maps Platform (Places Autocomplete, Maps
SDK, Directions API) requires a Google Cloud billing account on file even
to stay within its free tier, plus react-native-maps and native config —
real cost and build time neither justified for an FYP. Instead used Expo's
built-in expo-location module, which geocodes a typed address into
lat/lng client-side via the device's own OS geocoder (Apple's on iOS,
Google's via Play Services on Android) — no API key, no billing account,
no ongoing cost. No map view, no autocomplete dropdown, no route
polylines — coordinates exist purely to power distance-based search.

Backend (backend/apps/rides/, backend/common/):
- Ride gained four nullable fields: departure_lat/lng, destination_lat/lng
  (FloatField, not DecimalField — these feed distance math, not money).
  Migration 0002, purely additive, no data migration.
- New backend/common/geo.py: haversine_km(lat1, lng1, lat2, lng2), pure
  stdlib math — no GeoDjango/PostGIS, deliberately not reopening that
  constraint. Self-checked with two TestCase methods in common/tests.py
  (a known ~111.2km reference distance, and a same-point-is-zero check).
- RideSerializer validates that a leg's lat and lng are always supplied
  together — one without the other is a 400.
- RideListCreateView.get_queryset(): when a leg's ?<leg>_lat=&<leg>_lng=
  query params are present, that leg switches from icontains substring
  matching to haversine proximity within a radius (?radius_km=, default
  5km) — but with an OR-fallback: a ride whose matching leg was never
  geocoded (null coordinates) still falls back to substring-matching its
  text, so a ride that failed to geocode is never silently dropped from
  search just because the searcher's client resolved coordinates and it
  didn't. Filtering happens in Python once coordinates are involved
  (haversine isn't expressible in plain Postgres without PostGIS) — a
  deliberate call at this row count (low hundreds of rides), where a full
  Python pass is microseconds and a bounding-box SQL pre-filter would be
  unrequested complexity for no measurable gain. When no coordinates are
  supplied at all, the query path is byte-for-byte the original
  substring-only logic — zero behavior change for any caller that doesn't
  opt in.

Mobile (mobile/src/features/rides/):
- New dependency: expo-location (matched to the project's Expo SDK ~57).
  app.json plugins gained an expo-location entry with a
  locationWhenInUsePermission string — foreground-only, since this is
  one-shot geocoding, never background tracking.
- New data/geocode.ts: geocodeAddress(text) wraps
  requestForegroundPermissionsAsync() + geocodeAsync(), guarded by a 5s
  timeout race so a hung OS geocoder mid-demo can't block ride submission.
  Never throws — every failure path (permission denied, empty result,
  network error, timeout) resolves to null. Permission is requested lazily
  on first use, not on screen mount.
- OfferRideScreen and RideListScreen both geocode departure/destination in
  parallel (Promise.all) on submit, attaching lat/lng to the request only
  for whichever leg resolved — independently, so one failed leg doesn't
  block the other. Permission-denied UX is silent fallback to text-only,
  no dialog, no blocking state — geocoding is best-effort enrichment,
  never a hard requirement, matching how the rest of this module already
  degrades gracefully.
- ridesApi.ts types extended (Ride, CreateRidePayload, RideSearchParams)
  with the four optional/nullable coordinate fields plus an unused-by-UI
  radius_km search param (type-only, no slider control — nobody asked for
  one).

Verified: `manage.py test common` — both haversine self-checks pass.
Django-shell sanity check against realistic Lahore coordinates confirmed
proximity matching correctly includes a ~1.3km-away point and excludes a
~15km-away point at the 5km default radius, and confirmed the
ungeocoded-ride text fallback works in both the match and no-match
direction. `npx tsc --noEmit` clean. Expo web bundle still compiles with
the new dependency. `manage.py check` clean.

Known limitation carried forward: still no visual map, no address
autocomplete while typing, no real route/polyline overlap — this is
proximity-based precision on top of text search, not a full Maps
