2026-08-07 — Built the User Profiles + Auth base module (backend + mobile).

Backend (/backend, Django 5.2 + DRF, Postgres db "fyp_dev"):
- accounts.User: custom AbstractBaseUser keyed on email (no username field).
  Fields: email, full_name, department, enrollment_year, role
  (student/admin), is_email_verified, is_active (starts False), timestamps.
- accounts.EmailVerification: one-time 6-digit code + 15-minute expiry, tied
  to a user. Registration only accepts @lgu.edu.pk addresses (checked in the
  serializer, not the model, so admin-created accounts aren't blocked by it).
- Five endpoints under /api/auth/: register, verify-email, login (custom
  simplejwt serializer that rejects unverified/inactive accounts), refresh,
  me (GET/PATCH own profile). Full request/response shapes documented in
  docs/api-contracts/auth.md.
- Email delivery uses Django's console backend for now (OTP prints to the
  runserver log) — real SMTP deferred until the project has a provider
  picked, matching the other deferred-infra decisions in system_design.md.
- Settings split into config/settings/{base,dev,prod}.py; DB creds and
  secret key read from backend/.env (gitignored, never committed).
- Moderation/account deactivation stays manual via Django admin
  (accounts.User is registered there with role/status filters) — no
  automation source exists for syncing against university enrollment data.
- Swagger/OpenAPI docs live at /api/docs/ once the server is running
  (drf-spectacular) — that becomes the source of truth over the markdown
  contract from here on.

Mobile (/mobile, Expo SDK 57 + Expo Router + TypeScript):
- Feature-first layout: src/core/network/apiClient.ts (axios instance,
  attaches the JWT access token, auto-refreshes once on a 401 and retries
  the original request), src/core/auth/session.ts (Zustand store for
  user/tokens, persisted through expo-secure-store, not AsyncStorage, since
  tokens are secrets).
- src/features/auth/: data/authApi.ts wraps the five endpoints;
  presentation/ has Register, VerifyEmail, Login, and Profile screens;
  auth.ts barrel file is the only import surface other features may use.
- app/ is routing only: (auth)/{login,register,verify-email} and
  (app)/profile route files just re-export the screen components.
  app/_layout.tsx hydrates the session on launch and redirects based on
  whether an access token is present.
- Verified end-to-end: backend flow tested directly against the live
  Postgres db (register -> read OTP from console -> verify -> login ->
  authenticated /me, plus rejection cases for bad domain, wrong code, and
  unverified login). Mobile side type-checked clean and bundled successfully
  through Metro (expo export -p android, 1206 modules, no errors).

Known limitations carried forward from system_design.md: OTP email is
console-only in dev, moderation/deactivation is a manual admin toggle, and
this module runs on PostgreSQL locally (already installed on this machine,
so no SQLite fallback was needed).

2026-08-07 (later) — Added an official-student roster gate to registration.

Registering with an @lgu.edu.pk address is no longer sufficient on its own —
the email must also appear in a new accounts.StudentRoster whitelist table
(email only, unique). Loaded via a management command:
  manage.py import_roster <path-to-csv> [--dry-run]
The command looks for a column named "email" (case-insensitive) in the CSV
and ignores every other column, so the university's export can carry
whatever extra fields (student ID, name, etc.) it already has without a
custom importer. Re-running against an updated CSV is safe — existing
entries are left alone (get_or_create), only new emails are added.

RegisterSerializer.validate_email now checks the roster after the domain
suffix check and before the "already registered" check, with its own error
message ("This email isn't on the official LGU student roster..."). Nothing
else in the registration/verification/login flow changed — a roster hit
still requires setting a password and completing OTP verification, same as
before. StudentRoster is also registered in Django admin for manual
spot-checks, even though CSV import is the primary way it gets populated.

Verified: imported a 2-row test CSV (with extra ignored columns), confirmed
a roster email can register (201) and a same-domain but non-roster email is
rejected (400) with the new message. Test data cleaned from fyp_dev after.

2026-08-08 — Added a browser-based auth test console (dev only, no build).

Salman found curl/Swagger testing confusing to drive by hand, so added a
single-page HTML+vanilla-JS console at /test/ that exercises the whole auth
flow by clicking buttons instead of typing requests: add an email to the
roster, register, verify, log in, then GET/PATCH the profile, with every
raw request/response logged on the page as it happens. Lives at
backend/accounts/templates/accounts/test_console.html, served by a
TemplateView. Same-origin fetch calls, so no CORS setup needed beyond what
already exists.

Two small backend additions to support it, both dev-only:
- RegisterView now includes a "debug_otp" field in its response when
  settings.DEBUG is True, so the console can auto-fill the verification
  code instead of needing the runserver console open in another window.
  Leaks nothing new since the OTP already prints to that console in dev.
- New DebugAddRosterView (POST /api/auth/debug/add-roster/) lets the
  console add a one-off test email to StudentRoster without running the
  CSV import command for every throwaway address.

Both the page and the debug endpoint are only wired up inside an
`if settings.DEBUG:` block in config/urls.py, and DebugAddRosterView
double-checks settings.DEBUG itself and 404s otherwise — neither exists
when DEBUG=False (i.e. never in prod).

Verified the full click-through path end-to-end via curl standing in for
the button clicks: add-roster -> register (got debug_otp back) -> verify
-> login -> GET /me -> PATCH /me, all against a freshly started server.
Test data cleaned from fyp_dev after.

Side note: hit a real gotcha while testing this — a previous background
runserver process wasn't fully killed (the tracked shell died but the
child python.exe survived as an orphan on Windows), so a new runserver
invocation silently lost the port race and stale process kept answering
requests. Symptom was a confusing TemplateDoesNotExist on the new template
even though the file existed on disk. Fix was checking `netstat -ano` for
port 8000 and force-killing the orphaned PID before restarting. Worth
remembering if a future change to this backend "isn't taking effect" after
a restart — check for a leftover process on the port first.
