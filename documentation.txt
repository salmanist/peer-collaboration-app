2026-08-07 — Built the User Profiles + Auth base module (backend + mobile).

Backend (/backend, Django 5.2 + DRF, Postgres db "fyp_dev"):
- accounts.User: custom AbstractBaseUser keyed on email (no username field).
  Fields: email, full_name, department, enrollment_year, role
  (student/admin), is_email_verified, is_active (starts False), timestamps.
- accounts.EmailVerification: one-time 6-digit code + 15-minute expiry, tied
  to a user. Registration only accepts @lgu.edu.pk addresses (checked in the
  serializer, not the model, so admin-created accounts aren't blocked by it).
- Five endpoints under /api/auth/: register, verify-email, login (custom
  simplejwt serializer that rejects unverified/inactive accounts), refresh,
  me (GET/PATCH own profile). Full request/response shapes documented in
  docs/api-contracts/auth.md.
- Email delivery uses Django's console backend for now (OTP prints to the
  runserver log) — real SMTP deferred until the project has a provider
  picked, matching the other deferred-infra decisions in system_design.md.
- Settings split into config/settings/{base,dev,prod}.py; DB creds and
  secret key read from backend/.env (gitignored, never committed).
- Moderation/account deactivation stays manual via Django admin
  (accounts.User is registered there with role/status filters) — no
  automation source exists for syncing against university enrollment data.
- Swagger/OpenAPI docs live at /api/docs/ once the server is running
  (drf-spectacular) — that becomes the source of truth over the markdown
  contract from here on.

Mobile (/mobile, Expo SDK 57 + Expo Router + TypeScript):
- Feature-first layout: src/core/network/apiClient.ts (axios instance,
  attaches the JWT access token, auto-refreshes once on a 401 and retries
  the original request), src/core/auth/session.ts (Zustand store for
  user/tokens, persisted through expo-secure-store, not AsyncStorage, since
  tokens are secrets).
- src/features/auth/: data/authApi.ts wraps the five endpoints;
  presentation/ has Register, VerifyEmail, Login, and Profile screens;
  auth.ts barrel file is the only import surface other features may use.
- app/ is routing only: (auth)/{login,register,verify-email} and
  (app)/profile route files just re-export the screen components.
  app/_layout.tsx hydrates the session on launch and redirects based on
  whether an access token is present.
- Verified end-to-end: backend flow tested directly against the live
  Postgres db (register -> read OTP from console -> verify -> login ->
  authenticated /me, plus rejection cases for bad domain, wrong code, and
  unverified login). Mobile side type-checked clean and bundled successfully
  through Metro (expo export -p android, 1206 modules, no errors).

Known limitations carried forward from system_design.md: OTP email is
console-only in dev, moderation/deactivation is a manual admin toggle, and
this module runs on PostgreSQL locally (already installed on this machine,
so no SQLite fallback was needed).

2026-08-07 (later) — Added an official-student roster gate to registration.

Registering with an @lgu.edu.pk address is no longer sufficient on its own —
the email must also appear in a new accounts.StudentRoster whitelist table
(email only, unique). Loaded via a management command:
  manage.py import_roster <path-to-csv> [--dry-run]
The command looks for a column named "email" (case-insensitive) in the CSV
and ignores every other column, so the university's export can carry
whatever extra fields (student ID, name, etc.) it already has without a
custom importer. Re-running against an updated CSV is safe — existing
entries are left alone (get_or_create), only new emails are added.

RegisterSerializer.validate_email now checks the roster after the domain
suffix check and before the "already registered" check, with its own error
message ("This email isn't on the official LGU student roster..."). Nothing
else in the registration/verification/login flow changed — a roster hit
still requires setting a password and completing OTP verification, same as
before. StudentRoster is also registered in Django admin for manual
spot-checks, even though CSV import is the primary way it gets populated.

Verified: imported a 2-row test CSV (with extra ignored columns), confirmed
a roster email can register (201) and a same-domain but non-roster email is
rejected (400) with the new message. Test data cleaned from fyp_dev after.

Side note: hit a real gotcha while testing this — a previous background
runserver process wasn't fully killed (the tracked shell died but the
child python.exe survived as an orphan on Windows), so a new runserver
invocation silently lost the port race and stale process kept answering
requests. Symptom was a confusing TemplateDoesNotExist on the new template

Resource Sharing Module
Backend Django app: `resource_sharing`.
This module will manage resource listings, interest requests, real-time chat, and post-exchange ratings.

Mobile Resource Sharing currently includes typed API helpers and an authenticated Resource Feed screen. The route is `/resources` within the authenticated Expo Router group and displays active listings with pull-to-refresh, loading, empty, and error states.
Authenticated users can open the Resource Feed from the Profile screen through the Browse Resources button.

For testing with Expo Go on a physical device, `mobile/.env.local` sets `EXPO_PUBLIC_API_URL` to the development computer's current local-network address. The phone and computer must be on the same Wi-Fi network.

The mobile project currently uses Expo SDK 54 so that it is compatible with Expo Go 54 on Zahra's phone. Its Expo, Expo Router, React Native, React, and supporting package versions were aligned using Expo's compatibility checker. Run `npx expo start` from `mobile` and scan the displayed QR code with Expo Go; do not use `--android` unless testing with an Android emulator.

The computer's Wi-Fi IP can change when it reconnects to a network. If the browser or Expo Go reports that it cannot reach Django, update `EXPO_PUBLIC_API_URL` in the ignored `mobile/.env.local` file to the current Wi-Fi IPv4 address, then restart Expo with a cleared cache.

For this local setup, `EXPO_PUBLIC_WEB_API_URL` points to localhost for the browser, while `EXPO_PUBLIC_API_URL` points to the computer's Wi-Fi IPv4 address for Expo Go on the phone. Restart Expo after changing either value.

WiFi Configuration & Resilience (2026-08-18)
Created src/core/network/wifiDetection.ts to centralize WiFi IP handling. The utility:
- Parses EXPO_PUBLIC_API_URL from .env.local and extracts the IPv4 address.
- Exports resolveApiBaseUrl(): async function that returns the correct API URL per platform (localhost for web, configured WiFi IP for Expo Go).
- Exports logWiFiConfig(): debug helper that prints current config and env vars if connection fails.
- No external dependencies beyond React Native / Expo (SDK 54 compatible).

Updated src/core/network/apiClient.ts:
- initializeApiClient() now calls resolveApiBaseUrl() at app startup to set API_BASE_URL dynamically.
- Added debugApiConnection() helper for troubleshooting connectivity.
- JWT token attach and auto-refresh logic unchanged.

Updated app/_layout.tsx:
- Calls initializeApiClient() during session hydration so the API URL is resolved early (before auth or feature screens load).

Workflow when WiFi IP changes:
1. If browser or Expo Go can't reach Django, check your computer's current IPv4 (Windows: `ipconfig`, Mac/Linux: `ifconfig`).
2. Update EXPO_PUBLIC_API_URL in mobile/.env.local (e.g., `http://192.168.0.120:8000/api`).
3. Restart Expo: press 'r' in the terminal or reload the app in Expo Go menu.
4. If still stuck, run debugApiConnection() from the browser console (web) or Expo Go logs to see the resolved URL and env config.

Future enhancement: implement automatic IP detection using device APIs if Expo SDK adds platform-specific WiFi discovery (would eliminate manual .env.local updates).

The mobile login form reports a clear connection message when it cannot reach Django. Server-supplied authentication messages, such as an unverified email or invalid credentials, are displayed directly to the student.

Students can add a resource from the Resource Feed. The authenticated `/resources/create` screen collects its title, optional course, category, condition, sharing type, optional sale price, and description. It validates required fields locally, sends the listing to `POST /api/resources/`, and returns to the feed after a successful publish.

The Resource Sharing route group has its own stack navigator. It explicitly registers the feed (`/resources`) and create-listing (`/resources/create`) screens so they work consistently in Expo Go.

The authenticated app group also has a stack navigator. It registers the profile and Resource Sharing navigator, allowing Expo Router to resolve the nested Resource Sharing routes on a physical device.

The Resource Detail screen lives at `/resources/[id]`. It requests one listing from `GET /api/resources/<id>/` and displays its exchange terms, metadata, owner, and description. The interest button is visual at this stage; request creation is the next Resource Sharing feature.

Resource Interest Requests are now functional. From a listing owned by another student, a requester can submit an optional message through `POST /api/resources/<resource_id>/requests/`. The Resource Requests screen shows incoming and sent requests. Owners can accept, decline, and complete a request, while requesters can cancel a pending or accepted request. `PATCH /api/resources/requests/<request_id>/status/` applies those permissions and transitions the related listing between active, reserved, and unavailable where appropriate.

The same Expo app can be run in a browser. On Android and iOS, session tokens remain in Expo SecureStore. On web, the session store uses browser localStorage because the SecureStore native implementation is not available there. Web storage is suitable for local development; the native app remains the preferred place for mobile-session testing.

The My Resources dashboard at `/resources/mine` shows only the authenticated owner's listings through `GET /api/resources/mine/`. Owners can set a listing to active, reserved, or unavailable using the existing protected status API. The Profile screen provides direct links to Browse Resources, My Resources, and Resource Requests.

Resource Sharing now has three clear areas. Browse Resources (`/resources`) shows offers to sell, lend, exchange, give free, or rent. Request Resources (`/resources/wanted`) shows public posts from students looking for an item. My Resources (`/resources/mine`) is a hub with My Listings and My Requests. Students create public wanted posts at `/resources/wanted/create` and manage their own posts at `/resources/wanted/mine`, including marking a request fulfilled or cancelled. These posts are backed by `PublicResourceRequest`, with migration `resource_sharing.0002_alter_resourcelisting_exchange_type_and_more` applied to the local database. Private responses to a particular offer remain available separately as Interest Requests.

Browse Resources is intentionally read-only. Students add offers through My Resources > My Listings, and create public wanted-resource posts through My Resources > My Requests.

My Listings supports editing and deleting a listing. The edit screen uses the existing owner-protected `PATCH /api/resources/<id>/` endpoint, while deletion uses `DELETE /api/resources/<id>/`. A confirmation prompt appears before deletion. Only the listing owner can perform either action.

Live chat is available only after an interest request is accepted. The listing owner and accepted requester can open the chat from Interest Requests. Previous messages are retrieved through `GET /api/resources/requests/<request_id>/messages/`; new messages are sent and received live using `ws://<backend-host>/ws/resources/requests/<request_id>/chat/?token=<access-token>`. Messages are stored in Neon as `ResourceChatMessage` (migration `resource_sharing.0003_resourcechatmessage`). Daphne is first in `INSTALLED_APPS`, so `manage.py runserver` is WebSocket-capable in development. The current development setup uses Channels' in-memory layer, which supports real-time chat while one Django server process is running. A deployed multi-process backend needs a Redis channel layer.

The connected Neon database already contained legacy `gender` and roster-profile columns. Accounts migrations `0003_align_existing_neon_profile_columns` and `0004_align_gender_with_existing_neon_schema` align Django's models with that schema without deleting existing data. The default gender value is `other` because Neon stores that legacy field as `varchar(6)`. Registration still requires a roster entry, then creates the user and a six-digit OTP verification record normally.

The development-only browser authentication test console and `/test/` route have been removed. The actual authenticated API remains under `/api/auth/`; the DEBUG-only roster helper is retained for local development.

In My Resources > My Requests, a student can edit an open public resource request or delete any request they own after a confirmation prompt. Editing uses `PATCH /api/resources/wanted/<id>/`; deletion uses `DELETE /api/resources/wanted/<id>/`. Both endpoints remain owner-protected by the backend.

Every authenticated screen now shares the same project navigation. On wider web layouts it is a permanent left sidebar; on Expo Go and narrow screens, the Menu button opens the same sidebar. Logout is deliberately positioned at the top of this navigation and clears the stored session before returning to Login.

Public Resource Requests now support offers of help. A student browsing another student's open request can select Send Offer and add an optional message. This creates a `PublicResourceOffer` through `POST /api/resources/wanted/<request_id>/offers/`. The original requester sees these under My Resources > My Requests and can accept or decline each offer. Accepting an offer sets the public request to fulfilled and automatically declines any competing pending offers. The helper's sent-offer status is visible in Request Resources. The feature is stored in Neon through migration `resource_sharing.0004_publicresourceoffer`.

My Resources > My Requests also contains Offers I Sent. It shows each public request a student responded to, the offer message, and its pending, accepted, declined, or cancelled status. A student can cancel only their own pending offer.

To keep this area easy to scan, My Resources > My Requests uses three tabs: My Requests, Received Offers, and Sent Offers. Each tab shows only its relevant list while retaining the same creation, management, acceptance, decline, and cancellation actions.

The authenticated sidebar checks every 30 seconds for new active Browse Resources listings and new incoming Interest Requests. A green dot appears beside the relevant sidebar item when something was created after that user last opened its list. Opening Browse Resources or Interest Requests marks that list as read and removes its dot. These per-user read times are stored securely on a mobile device and in browser local storage for web development. Live chat now includes a one-line header summary naming the resource being discussed.

The sidebar groups all Resource Sharing navigation beneath an expandable Share Point section: Browse Resources, My Resources, Request Resources, and Interest Requests. This keeps the project navigation shorter while retaining direct access to each feature.

Both Resource Sharing agreement flows now have real-time chat. An accepted Browse Resources interest request uses `ResourceChatMessage`; an accepted public resource offer uses `PublicResourceOfferChatMessage` (migration `resource_sharing.0005_publicresourceofferchatmessage`). In both cases, only the two participants can read the history or connect to the WebSocket. Public-offer history is available at `GET /api/resources/wanted/offers/<offer_id>/messages/` and its live WebSocket is `ws://<backend-host>/ws/resources/offers/<offer_id>/chat/?token=<access-token>`. The requester and helper receive an Open Chat button after acceptance.

2026-08-19 — Built the Lost & Found Module (Backend + Mobile)

The Lost & Found module enables Lahore Garrison University students to post lost and found items, search by category and campus location, submit proof-of-ownership claims, and coordinate physical handover via real-time chat with photo sharing.

Backend (/backend/lost_and_found):
- Models (PostgreSQL):
  - LostAndFoundItem: poster (FK accounts.User), post_type (lost/found), title, category (electronics, cards_documents, stationery, clothing, accessories, keys, other), location, date_lost_or_found, description, image (optional ImageField), status (open, claimed, resolved, cancelled), timestamps, and composite performance indexes.
  - ItemClaim: item (FK LostAndFoundItem), claimant (FK accounts.User), message, status (pending, accepted, declined, withdrawn), timestamps.
  - ItemClaimChatMessage: claim (FK ItemClaim), sender (FK accounts.User), body, image (optional ImageField), created_at.
- REST API Endpoints (/api/lost-and-found/):
  - GET/POST /api/lost-and-found/: Filterable feed (post_type, category, status, search, location) and notice creation with optional photo upload.
  - GET/PATCH/DELETE /api/lost-and-found/<id>/: Item detail, owner updates, and owner deletion.
  - PATCH /api/lost-and-found/<id>/status/: Quick status transition (open <-> resolved).
  - GET /api/lost-and-found/mine/: User's own posted notices.
  - POST /api/lost-and-found/<item_id>/claims/: Submit claim/inquiry with ownership proof.
  - GET /api/lost-and-found/claims/incoming/: Claims received on user's posted notices.
  - GET /api/lost-and-found/claims/mine/: Claims submitted by user on others' notices.
  - PATCH /api/lost-and-found/claims/<claim_id>/status/: Accept/decline (by poster) or withdraw (by claimant). Accepting automatically marks item as claimed.
  - GET/POST /api/lost-and-found/claims/<claim_id>/messages/: Accepted claim chat history and photo messages with automatic WebSocket broadcast.
  - GET /api/lost-and-found/summary/: Lightweight notification counter for sidebar badge updates.
- Real-time WebSocket:
  - ws://<backend-host>/ws/lost-and-found/claims/<claim_id>/chat/?token=<jwt-token> served by ItemClaimChatConsumer for live handover coordination.

Mobile (/mobile/src/features/lost_and_found):
- Types & API: `lostAndFound.ts`, `data/lostAndFoundApi.ts` with cross-platform photo upload (`Blob` support on web, native multipart descriptors on iOS/Android).
- Notification Store: `lostAndFoundNotifications.ts` with Zustand store and AppState-aware background polling.
- Presentation Screens:
  - LostAndFoundFeedScreen: Tabbed feed (All, Lost Items, Found Items), category filter chips, campus location tags, search bar, and infinite scroll virtualization.
  - CreateLostAndFoundScreen: Post creation with type toggle (I Lost vs I Found), category, campus location, date, description, and optional photo attachment.
  - EditLostAndFoundScreen: Notice editing and photo replacement.
  - LostAndFoundDetailScreen: Full photo banner with full-screen zoom modal, poster profile card, claim modal for finders/owners, and post management actions.
  - MyLostAndFoundScreen: 3 tabs (My Notices, Incoming Claims with Accept/Decline, Sent Claims).
  - ClaimChatScreen: Real-time handover chat with photo attachments and modal zoom viewer.
- Navigation:
  - Expandable "Lost & Found" section integrated in AppSidebar with real-time green notification dots.
