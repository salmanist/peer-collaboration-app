--------------------------------------------------------------------
ACCOUNTS / AUTH (base module, salman)
--------------------------------------------------------------------
Stack: Django 5.2 + DRF + SimpleJWT, custom email-based User model (AUTH_USER_MODEL = accounts.User).

Flow:
  1. POST /api/auth/register/  { email, password }
     - email must end in @lgu.edu.pk AND already exist in StudentRoster (whitelist), else 400.
     - Creates User with is_active=False, is_email_verified=False.
     - Sends a 6-digit OTP (EmailVerification row, 15 min expiry) via console email backend in dev.
     - DEBUG=True responses include debug_otp so no email inbox is needed for local testing.
  2. POST /api/auth/verify-email/  { email, code }
     - Flips is_active=True, is_email_verified=True on match.
  3. POST /api/auth/login/  { email, password }  -> SimpleJWT token pair.
     - Custom EmailVerifiedTokenObtainPairSerializer re-checks is_active/is_email_verified after
       the standard SimpleJWT auth step and returns the user object alongside the tokens.
     - NOTE: SimpleJWT's own auth step fails first (and identically) on either a wrong password
       OR an inactive account - both produce the generic "No active account found with the given
       credentials" message. Don't assume that message means "unverified email"; check the DB.
  4. GET /api/auth/me/ (JWT required) - read-only, no PATCH (nothing user-editable left on User).

User profile fields (full_name, department, enrollment_year, gender) are NOT stored on User.
They are read-only Python @property lookups onto StudentRoster by email match (single source of
truth, imported via manage.py import_roster <csv> or, in DEBUG only, POST /api/auth/debug/add-roster/).

Database: shared Neon Postgres (see backend/.env, gitignored). Both salman and zahra's local
backends point at the same instance - no local Postgres involved.

KNOWN DB SCHEMA CAVEAT (fixed 2026-08-24, keep in mind for future migrations):
  The live Neon accounts_user/accounts_studentroster tables have drifted from django_migrations
  history before (migrations recorded as applied without the underlying ALTER TABLE actually
  landing - happened at least once with full_name in 2026-08-18, and again with 5 columns in
  2026-08-24). If a fresh INSERT ever throws IntegrityError on a column the current model doesn't
  define, check live schema directly before assuming the code is wrong:
    SELECT column_name, is_nullable FROM information_schema.columns WHERE table_name='...';
  StudentRoster deliberately still carries a nullable, unused phone_number column (kept at
  salman's request 2026-08-24) - not a bug, don't "clean it up" without asking first.
  Fixed 2026-08-28: the same drift bit StudentRoster's old free-text "department" column -
  migration 0007's RemoveField was recorded as applied but the DROP COLUMN never landed on
  Neon, so it sat there dead (holding stuff like "BSCS") alongside the real department_id FK
  the model actually uses. Migration 0008 (plain RunSQL) dropped it for real.
  Also live on accounts_studentroster: a separate dept_id FK column (also -> common_department)
  that this checkout's code does NOT use at all - confirmed real (not dead: has its own FK
  constraint) but unexplained, likely from someone else's migration on the shared DB. Left
  untouched deliberately - don't drop or repurpose it without figuring out who/what it's for.

DIGITAL LIBRARY (salman)
--------------------------------------------------------------------
backend/apps/library/. See docs/api-contracts/library.md.
Upload/list/detail/upvote/bookmark student projects, edit/delete own projects (author-only,
PATCH resets status to pending for re-moderation, DELETE is permanent), moderation via Django
admin bulk actions. LibraryProject.level (simple/semester/fyp, default simple) tags a project's
scope - "simple" shows no badge anywhere; semester/fyp show a corner badge (tertiary/secondary
tone respectively - do NOT use Badge's "primary" tone alongside "tertiary" for two different
tags, they render as the identical color in this theme) on every project card (LibraryListScreen,
MyProjectsScreen, LibraryDetailScreen). Picked on submit and editable afterward via the shared
LevelPicker component (features/library/presentation/).
LibraryProject.github_link (URLField, optional) holds an optional link to the project's repo,
shown as a tappable link on the detail screen. Attachments are LibraryProjectFile rows (FK to
project, no file-type restriction) instead of a single document field - a project can attach any
mix of files (PDF report, slides, zipped source, images, etc.) via multipart "files" parts;
upload form's "Add Files" button opens the native multi-file picker with no type filter.
LibraryListScreen hero layout, top to bottom: "Digital Library" heading, a Projects/Notes tab
row (segmented pills, translucent-white inactive/primaryFixed active - styled for the dark hero
background), then a row of 4 icon-only nav pills (roadmap/"My projects" or "My notes"/"Print
centre"/upload), then the search bar. "My projects" (mobile/app/(app)/library/my-projects.tsx ->
MyProjectsScreen) is wired to GET /api/library/mine/ - shows the signed-in user's own submissions
regardless of status (pending/approved/rejected), each with a status badge, mirroring
MyRidesScreen's pattern. Each row has Edit (-> EditProjectScreen, app/(app)/library/[id]/edit.tsx,
PATCHes title/department/abstract/github_link only) and Delete (confirm dialog, DELETE) actions.
"Print centre" is still a reserved nav pill with no screen behind it - planned as its own
future module.
Department filter on LibraryListScreen is a dropdown (core/ui/DepartmentPicker with clearable
prop, full department names shown - not short codes), not chips, sitting in a filterRow wrapper
left ready for more filters beside it. DepartmentPicker.onChange is (Department | null) => void -
null means "cleared"/"All Departments", used only by clearable callers; the required-field
upload/edit forms don't pass clearable and never see null in practice.
FYP Roadmap (app/(app)/library/roadmap.tsx -> RoadmapScreen, linked from a map-icon pill on
LibraryListScreen's hero) is a static guidance screen, not backed by any API - a numbered list of
the 7 stages every FYP goes through (Idea & Proposal, Requirements/SRS, Design, Development,
Testing & QA, Documentation, Defense & Submission), each with a timeframe, summary, and tips.
All the copy lives in src/features/library/presentation/roadmapContent.ts (roadmapIntro string +
roadmapStages array) - edit that file to change the guidance text, RoadmapScreen.tsx only renders
whatever's in it.

NOTES SHARING - a second content type nested inside this same module (not a separate app, not a
separate module), reached via the Projects/Notes tab on LibraryListScreen rather than its own
screen. Note/NoteFile (backend/apps/library/models.py) mirror LibraryProject/LibraryProjectFile's
shape closely but with NO status/moderation field at all - a note is publicly visible the instant
it's created. Fields: title (heading), a required course FK (see below), optional semester
free-text tag, optional description, files (same multi-file attachment pattern as Projects).
Endpoints under the same /api/library/ prefix: notes/, notes/mine/, notes/<pk>/,
notes/<pk>/upvote/, notes/<pk>/bookmark/ - same author-only-edit/delete, upvote/bookmark-toggle
patterns as Projects, just without the moderation branch.
Course dropdown (mobile: core/ui/CoursePicker.tsx, a DepartmentPicker sibling with a search box
since it's 143 rows deep) is backed by common.AcademicCourse - a READ-ONLY, Meta.managed=False
Django model pointed at peer_tutoring_academiccourse, a real table already live on the shared
Neon DB from a Peer Tutoring build with no matching app in this checkout (not in INSTALLED_APPS).
This app never migrates, alters, or writes to that table - common/admin.py's AcademicCourseAdmin
explicitly disables add/change/delete. Exposed at GET /api/courses/ (config/urls.py, alongside
/api/departments/), with pagination_class=None since 143 rows exceeds DRF's default PAGE_SIZE=20
and CoursePicker caches+filters the whole list client-side (same usePersistentCache pattern as
DepartmentPicker). Remove common.AcademicCourse once a real Peer Tutoring app owns this table
directly instead.
Because Notes have no moderation lag masking staleness (unlike Projects, where a submission
sitting in "pending" already means it won't show in the public list yet), LibraryListScreen's
notes feed intentionally has NO cache-first read on focus (Projects' feed still does, via
DataStore) - a just-uploaded note needs to appear immediately, not after a stale cached "empty"
result expires.

MOBILE: PERSISTENT CACHE (core/data, salman)
--------------------------------------------------------------------
mobile/src/core/data/PersistentCache.ts - a second, longer-lived cache tier alongside the
in-memory DataStore below, for reference data that barely ever changes (departments today).
Backed by @react-native-async-storage/async-storage (installed this pass - genuinely wasn't
present before; on web it resolves to a plain localStorage-backed shim, not IndexedDB). Exposes
usePersistentCache<T>(key, fetcher, maxAgeMs=24h): shows whatever's on disk immediately
regardless of age, then silently refetches in the background if it's older than maxAgeMs and
updates both state and storage; nothing cached yet fetches normally. Needs no Context/Provider
(unlike DataStore) since AsyncStorage is already one shared module app-wide. Used by
LibraryListScreen's department filter chips, DepartmentPicker (core/ui/), and
EditProjectScreen's department pre-fill - all three share the same "departments" cache key.

MOBILE: SHARED IN-MEMORY CACHE (core/data, salman)
--------------------------------------------------------------------
mobile/src/core/data/DataStore.tsx - a React Context holding one in-memory Map (via useRef, so
writes don't force re-renders), exposed as getCache/setCache/clearCache through useDataStore().
Wrapped once at the app root (app/_layout.tsx) so every screen shares the same cache instance for
the app's session lifetime - memory only, not persisted to disk, cleared on a full reload.
LibraryListScreen and RideListScreen both use it for their default (unfiltered) list: on focus,
check the cache first and show it instantly if present (skip the network call entirely); only
fetch when empty, and save the result back right after a successful unfiltered fetch. A real
search/destination search always bypasses the cache. Both screens have a refresh button that
force-bypasses the cache for a genuine fresh fetch. Not used for anything auth-related (session
already has its own Zustand-backed persistent store, see ACCOUNTS/AUTH above) or for any
single-item detail screen (RideDetailScreen/LibraryDetailScreen) - only the two list screens.

MOBILE: SHARED UI (core/ui, salman)
--------------------------------------------------------------------
Skeleton.tsx - one pulsing gray block (Animated opacity loop, no new dependency), composed by
each screen into card-shaped loading placeholders. Used by RideListScreen/MyRidesScreen/

a maxHeight:"50%"/overflow:"hidden" sheet, so anything past what fit on screen was unreachable
once the department list grew past ~10 entries. One shared component, fixes every dropdown at once.

PRINT CENTRE (salman)
--------------------------------------------------------------------
Peer-to-peer printing: students ask, other students who registered as printers fulfil it. No
printer hardware integration and no pricing/payments (SRS 4.7, system_design.md scope cut).

Roles: every student is a requester. A student becomes a printer by registering from the
top-right "Register as printer" button on the Print Centre home (location note + colour and
double-sided switches); a PrinterProfile row is what marks them as a printer. They can stop being
one from the same screen (refused while they hold accepted jobs). Printers appear as cards (name,
department, location, capabilities, average star rating) on the Print Centre home.

Flow: requester uploads a document + settings (page range, copies, colour or B/W, single or
double-sided) and either taps a printer card (request is directed to that printer, hidden from the
open pool, printer notified) or posts it to the open pool. A printer accepts (requester notified).
A directed request can also be rejected by its target printer: it drops back into the open pool
and the requester is notified. After accepting, the printer prints and presses "Submit document"
with an optional collection note (status done, requester notified). The printer can release an
accepted job (reopens to everyone). The requester can cancel only while open. Once done, the
requester can rate the printer 1-5 stars with an optional comment, once per job. Only registered
printers can accept; nobody can accept their own request.

Views: plain students get "My requests" (past and current). Printers also get "My print jobs",
grouped as Sent to me, Open requests, In progress, Completed; a badge on that button counts
requests sent to them that are still waiting.

Backend (apps/printing/, mounted at /api/printing/): models PrinterProfile, PrintRequest (adds
nullable target_printer), PrintRating. Endpoints: GET / (open pool, undirected only), POST /
(multipart create, optional target_printer_id), GET mine/?role=requester|printer|incoming,
GET <id>/, POST <id>/accept|reject|release|complete|cancel|rate/, GET printers/ (annotated with
average rating + count in one query), GET/PUT/DELETE printers/me/. The state-changing actions
share one base view that row-locks the request (select_for_update) so two printers can't both
accept it. Documents: pdf/doc/docx/png/jpg only, max 20 MB; page_range must look like "1-5,8" or
be empty. Notifications reuse common.notify() and the existing /api/notifications/ list.

Mobile (features/printing/): PrintCentreScreen (home: register/settings pill, New request, My
requests, My print jobs, printers list), NewPrintRequestScreen (optional target printer),
MyRequestsScreen, MyPrintJobsScreen, PrinterRegisterScreen, PrintRequestDetailScreen (accept,
reject, submit, release, cancel, rate by role + status), shared bits in printUi.tsx. Routes under
app/(app)/printing/. Entry points: "Print Centre" in NAV_ITEMS (hamburger + bottom bar), the Home
tile, and the printer icon in Digital Library's hero. The bell opens the shared notifications
screen (rides/notifications).

BOTTOM NAVIGATION BAR (salman)
--------------------------------------------------------------------
Floating glass tab bar (WhatsApp/Instagram style): Home, Rides, Library, Print (the NAV_ITEMS
list in core/ui/HamburgerMenu.tsx, shared with the hamburger menu). Icons only; the active tab shows
the filled glyph (icon name without "-outline") in forest green, inactive tabs the outline glyph in
muted grey.

Look: a rounded pill (fully rounded ends) detached from the bottom - absolutely positioned 16px
from each side and lifted off the bottom by the safe-area inset + 12px - with a real backdrop blur
(expo-blur BlurView, intensity 50, light tint; CSS backdrop-filter on web) under a 20% white wash, a
translucent white hairline border and a soft shadow. The shadow sits on an outer view because the
glass view clips (overflow hidden) for the rounded corners.

It lives in app/(app)/_layout.tsx (the Stack fills the screen, BottomNavBar floats over it), so it
stays on every signed-in screen including sub-screens and is absent on login/register. The active
tab is read from the URL via useSegments() (segments[1] = home|rides|library|printing);
profile/announcements show no active tab. Switching tabs: dismissAll() then replace(), so the back
stack doesn't pile up; tapping the active tab calls dismissTo(href). Hidden while the keyboard is
open.

Content scrolls underneath the glass, so nothing reserves space for the bar. useNavClearance()
(BottomNavBar.tsx) returns bar height + gap + safe-area inset + 16px; ScreenContainer adds it as
bottom padding on scrolling screens inside (app), and every FlatList/SectionList screen passes
ListFooterComponent={NavClearance} (a spacer of the same height) so the last item can clear the
bar. New list screens need that footer too.

ON-DEMAND RIDE (salman) - Phase 1: roles and drivers
--------------------------------------------------------------------
Separate module (apps/ondemand) next to the trip board; the trip board (apps/rides) is untouched.
Depends only on the user module. API under /api/ondemand/.

Models: RideProfile (one per student: role driver|rider, vehicle make/model/colour/plate/seats for
drivers, is_approved flag). The role is picked once and is fixed - only an admin deleting the row lets
the student pick again. FareSetting is a single-row table holding rate_per_km (default Rs 30); read it
with get_rate_per_km().

Endpoints: GET /api/ondemand/profile/ (404 = no role picked yet), POST /api/ondemand/profile/ (creates
it once; drivers must supply all vehicle fields, plate is upper-cased; riders' vehicle fields ignored).

Admin centre (Django admin at /admin/): "Ride profiles" has role/approval filters and the actions
"Approve selected drivers" / "Remove approval"; "Fare settings" holds the editable rate per km (one row,
cannot add a second or delete it).

Mobile: Home card "On-demand Ride" -> app/(app)/ondemand -> OnDemandHomeScreen: choose Rider/Driver,
drivers fill the vehicle form, afterwards the screen shows role + approval status. Map and rides come
in later phases.

ON-DEMAND RIDE - Phase 2: map and fuel share
Place model (popular pick-up/drop-off spots, editable in admin) seeded by `manage.py reset_ondemand_demo`
(wipes and reseeds the places; later phases add demo drivers/riders to the same command).
GET /api/ondemand/places/ lists them. POST /api/ondemand/fare/ takes pickup/drop lat+lng and returns
distance_km, rate_per_km, fare (= distance x admin rate, rounded to the rupee), distance_source and the
route path. Distance comes from the free public OSRM server (road distance); if it fails or times out (5s)
it falls back to a straight line and says so. Plain http is used because this PC's Python rejects OSRM's
https certificate. Nothing is stored; money is paid outside the app.
Mobile: react-native-webview added (the map). RideMap.tsx draws OpenStreetMap with Leaflet inside a
WebView (needs internet; Android/iOS only, not the web build). BookRideScreen (riders only, via the
"Book a ride" button on the On-demand screen): pick pickup/drop-off from popular-place chips or by tapping
the map; the fare card appears automatically once both are set.

ON-DEMAND RIDE - Phase 3: requests, accept, status flow
Models: OnDemandRide (rider, driver, pickup/drop labels + coordinates, distance_km, fare, saved route
path, status, cancelled_by). RideProfile gained is_online, last_lat, last_lng, last_seen. A driver counts
as live only while is_online and last_seen is within 30 seconds (the phone sends its position every 5 s).
Statuses: requested -> accepted -> arrived -> in_progress -> completed, or cancelled / no_driver.
Endpoints (/api/ondemand/): driver/status/ (online/offline + position, approved drivers only),
driver/requests/ (open requests within 5 km of the driver, oldest first), rides/ (rider requests; fare and
route are recalculated on the server), rides/current/ (caller's active ride as rider or driver, polled every
5 s), rides/<id>/ (shows how a finished ride ended), rides/<id>/accept|arrived|start|complete|cancel/.
Rules: a user can have one active ride at a time; only riders request, only approved + live drivers accept.
First driver wins: accept locks the ride row, so a second driver gets 409 "already taken". Rider can cancel
until the trip starts; driver can cancel after accepting until it starts; a driver can't go offline mid-ride.
A request nobody accepts within 120 s becomes no_driver (checked lazily whenever someone asks).
Notifications (existing notify()) go to the rider on accept/arrived/start/complete and to the other side
on cancel.
Mobile: BookRideScreen got a Confirm ride button; ActiveRideScreen (both roles, polls every 5 s, shows
status, map, driver or rider card and the buttons that fit the role/status); DriverScreen (online switch,
GPS heartbeat every 5 s via expo-location, nearby requests with Accept); OnDemandHomeScreen links to them.
On the web build the map shows a note instead of the WebView.

RIDES HUB - Ride Sharing + On-demand Ride shown as one section (salman)
UI/navigation only: backend apps (apps/rides, apps/ondemand), databases and the trip board's own screens
are unchanged. Home and the menu/bottom bar have one "Rides" entry (route /(app)/rides). A shared
SegmentedSwitch (core/ui) sits at the top of both home screens ("Scheduled trips | On-demand") and moves
between /(app)/rides and /(app)/ondemand with router.replace. The Rides tab in the bottom bar stays lit on
on-demand screens. Home's "Next ride" card shows an active on-demand ride first (via getCurrentRide);
the trip board shows a banner "You have an on-demand ride in progress" when one exists.

ON-DEMAND RIDE - role change (replaces the Phase 1 "pick a role once" flow)
Nobody picks a role any more: everyone starts as a rider (the profile is created automatically the first
time GET /api/ondemand/profile/ is called). The On-demand home shows the pickup/drop-off fields, map, fuel
share and Confirm ride directly (the separate Book a ride screen is gone). A gear button on that screen
opens On-demand settings:
- Rider: "Become a driver" form (make, model, colour, plate, seats) -> POST profile/apply/. The profile
  becomes role=driver with is_approved=false = a pending application. While pending the student can still
  request rides as a rider. In the admin centre (Ride profiles) the admin ticks "Approve selected drivers",
  or "Reject selected driver applications" (back to rider, vehicle details cleared).
- Pending applicant: can withdraw (POST profile/stop-driving/).
- Approved driver: sees Driver mode on the home screen; settings has "Stop being a driver" (two-step
  confirm; refused while on an active ride) -> back to rider, vehicle details cleared, offline.
Approved drivers can't request rides (403). POST /api/ondemand/profile/ (old role picker) no longer exists.
The home hero shares the Scheduled trips layout; the first card is pulled up over the hero so both tabs line up.

ON-DEMAND RIDE - no driver found: the rider sees "Try again" (POST /api/ondemand/rides/<id>/retry/ sets the ride back to requested and restarts the 120 s wait; only the rider, only from no_driver) and "Cancel ride" (rider cancel is also allowed from no_driver).

DIGITAL LIBRARY - demo data: `python manage.py seed_library_demo` adds 10 dummy projects (approved/pending/rejected mix) and 12 dummy notes written by the existing test students, with dummy upvotes/bookmarks and no file attachments. Idempotent (matches on author + title); `--reset` deletes those dummy rows first.

RIDES HUB - one screen for on-demand + scheduled trips (replaces the Scheduled/On-demand tab switch)
Route /(app)/rides is now RidesHubScreen (features/rideshub, the only code that knows both modules; the
trip board and on-demand backends/modules stay independent, no backend change). Top to bottom: green hero
with round buttons (Offer a trip, My trips, On-demand settings, Notifications); then a first card by state -
active on-demand ride (Open), approved driver (Driver mode), otherwise the booking form (Pickup / Drop-off
fields with type-ahead + pin map, fuel share, Confirm ride) plus a "driver application pending" notice;
then "Scheduled trips" (all open trips; once a drop-off is chosen it becomes "Scheduled trips going your
way": destination-only matching via GET /api/rides/ destination_lat/lng, same rule as the old trip board).
TripCard/TripSkeletonList (rides/presentation) are the shared trip list pieces. /(app)/ondemand now just
redirects to /(app)/rides; ride/drive/settings screens still live under /ondemand and the Rides tab stays
lit there. SegmentedSwitch, RideListScreen and OnDemandHomeScreen were removed.

2026-08-07 (later) — Added an official-student roster gate to registration.

Registering with an @lgu.edu.pk address is no longer sufficient on its own —
the email must also appear in a new accounts.StudentRoster whitelist table
(email only, unique). Loaded via a management command:
  manage.py import_roster <path-to-csv> [--dry-run]
The command looks for a column named "email" (case-insensitive) in the CSV
and ignores every other column, so the university's export can carry
whatever extra fields (student ID, name, etc.) it already has without a
custom importer. Re-running against an updated CSV is safe — existing
entries are left alone (get_or_create), only new emails are added.

RegisterSerializer.validate_email now checks the roster after the domain
suffix check and before the "already registered" check, with its own error
message ("This email isn't on the official LGU student roster..."). Nothing
else in the registration/verification/login flow changed — a roster hit
still requires setting a password and completing OTP verification, same as
before. StudentRoster is also registered in Django admin for manual
spot-checks, even though CSV import is the primary way it gets populated.

Verified: imported a 2-row test CSV (with extra ignored columns), confirmed
a roster email can register (201) and a same-domain but non-roster email is
rejected (400) with the new message. Test data cleaned from fyp_dev after.

Resource Sharing Module
Backend Django app: `resource_sharing`.
This module will manage resource listings, interest requests, real-time chat, and post-exchange ratings.

Mobile Resource Sharing currently includes typed API helpers and an authenticated Resource Feed screen. The route is `/resources` within the authenticated Expo Router group and displays active listings with pull-to-refresh, loading, empty, and error states.

For testing with Expo Go on a physical device, `mobile/.env.local` sets `EXPO_PUBLIC_API_URL` to the development computer's current local-network address. The phone and computer must be on the same Wi-Fi network.

The mobile project currently uses Expo SDK 54 so that it is compatible with Expo Go 54 on Zahra's phone. Run `npx expo start` from `mobile` and scan the displayed QR code with Expo Go; do not use `--android` unless testing with an Android emulator.

The computer's Wi-Fi IP can change when it reconnects to a network. If the browser or Expo Go reports that it cannot reach Django, update `EXPO_PUBLIC_API_URL` in the ignored `mobile/.env.local` file to the current Wi-Fi IPv4 address, then restart Expo with a cleared cache.

For this local setup, `EXPO_PUBLIC_WEB_API_URL` points to localhost for the browser, while `EXPO_PUBLIC_API_URL` points to the computer's Wi-Fi IPv4 address for Expo Go on the phone. Restart Expo after changing either value.
